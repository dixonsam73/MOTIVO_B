# Études — Audit Finding Register

From a four-phase client audit and a Supabase backend audit at commit `ec2f52f`,
plus the migration baseline builds. The audit itself compiled nothing except at
migration — findings marked *(build)* came from the Release compile.

**Severity:** P0 critical · P1 release blocker · P2 important · P3 improvement.

**State** — deliberately separate from severity, and the column that moves as
work lands:

| State | Meaning |
|---|---|
| **Confirmed defect** | The code is wrong today. Evidence is in hand. |
| **Unverified** | Suspected, mechanism plausible, not yet established. The cell says what would settle it. |
| **Confirmed gap** | Factually true and worth tracking, but not a defect in behaviour (coverage, tooling, process). |
| **Product decision settled** | We know what the correct behaviour is. The code does not do it yet. |
| **Resolved** | The implementation now matches the decision, and that has been verified. |

The distinction between the last two is the point of this register. An item
moves to **Resolved** only when code has changed and been checked — never
because a design was agreed. C-23 and C-24 are Resolved; both were filed during
Phase 1 rather than by the audit. C-1 is the first audit finding to move, and it
is Resolved **for its client scope only** — the server half is tracked separately
as C-26. Where a state is qualified like that, read the cell rather than the
word.

## Activation path — observed behaviour, 2026-08-11

From `ActivationTrace` on instrumented TestFlight build 130, on real StoreKit.
**These are observations, not findings.** They are recorded because the
activation path had never been watched at runtime, two C-38 hypotheses died on
contact with this data, and the next person to touch this code should not have
to rediscover it.

**The healthy sequence.** Activation needs five gates and they satisfy in a
fixed order, not simultaneously — the last one to arrive is what flips the mode:

```
appOnAppear        entitled=false signedIn=false token=false backendID=false → solo
entitlementRead    resolved=entitled                     (~60 ms after launch)
membershipEntitled entitled=true  signedIn=false                             → solo
                   …Sign in with Apple…
membershipEntitled entitled=true  signedIn=true  token=false                 → solo
backendUserIDChanged              signedIn=true  token=true  backendID=false → solo
signIn stage=supabaseSessionStored signedIn=true token=true  backendID=true
membershipEntitled entitled=true  signedIn=true  token=true  backendID=true  → CONNECTED
```

The Apple credential (`signedIn`), the Supabase exchange (`token`) and the
derived `backendID` land as three separate steps roughly 1.3 s apart.

**`removeDuplicates()` does not dedupe across renders.** The activation triple —
`membershipEntitled`, `currentUserIDChanged`, `backendUserIDChanged` — fired
**thirteen times in twenty-one seconds**, clustered around UI events rather than
on a timer, and fired after a `membershipState entitled -> entitled
changed=false` write. SwiftUI reconstructs
`$membershipState.removeDuplicates()` on every body evaluation, and a fresh
publisher has no memory of prior values, so each re-subscription re-emits the
current one. **Any reasoning of the form "that transition is consumed and cannot
fire again" is unsafe here** — which is exactly how C-38's second explanation
died. Note this does *not* clear C-24, whose completion paths live in
`ProfileView` rather than on this publisher.

**`@Published` delivers to `onReceive` on `willSet`.** Activation is logged
*before* the `didSet` probe records the change. Ordering in these logs is not
evidence of causation running backwards.

**Two `refreshEntitlement` calls run concurrently at launch.** At 17:14:43.767,
`membershipState` reached `.entitled` *before* `entitlementRead` logged — only
possible if a waiter awaited the in-flight task and published its result first,
then the owner resumed to log its own read and publish the same value again.
`start()`'s refresh racing the `scenePhase == .active` refresh is the likely
pair. **Relevant to C-38 if it is ever confirmed:** `purchase()` calls
`refreshEntitlement(forceAfterCurrent: true)`, and if a refresh is already in
flight — which the StoreKit sheet dismissing makes likely, as C-13's cell warns —
the waiter path publishes that in-flight result *before* performing its forced
fresh read. That is a window for a stale value to be published, and it is a
different shape from the single-stale-read hypothesis C-38 currently carries.

**C-24 re-verified on real StoreKit.** The 17:21 run was a reinstall with a live
entitlement: routed past membership selection straight to sign-in, and reached
Connected cleanly. Previously verified under the synthetic configuration only.

**Expected residue, recorded so it is not filed twice.** The departing member's
received row named an object under **B's** prefix, and A's sweep only covers A's
prefix — so that object now has no reference at all. This is the unowned-object
lifecycle the function header already defers to B-8/B-10 in Phase 4. It was
predicted before the run rather than discovered after it.

### Whole-backend orphan sweep — 2026-08-11, read-only

Prompted by B-21: the old function ran for months, so the question was what else
it left behind. Answer: **very little, and nothing exposed.**

- **Zero orphaned `posts`** — B-4's worst case, rows unreachable by any RLS
  policy, never materialised.
- **Zero orphaned `post_shares`, `post_comment_views` or `follows`.**
- **Zero orphaned storage objects in `attachments`.** The avatars bucket was the
  only place with residue, which is precisely where the audit had no coverage.
- The only `post_comments` with a dead author or recipient are the two from
  D7/D8 earlier the same day — retained by decision, working as designed.
- 30 dead `connected_attachments` rows, none with surviving storage. Measured
  under B-9.

**One false positive, worth more than the sweep itself.** The first pass flagged
an orphaned attachments object by asking whether the uid in the path prefix still
existed in `auth.users`. It was D5's survivor. The prefix carries the **sender's**
uid, and a dead sender is the *correct* state for a preserved asset — so the
obvious cleanup heuristic destroys exactly what B-1 protects. That warning is now
recorded on B-8, which is where someone will eventually write that cleanup.

**Two client-side gaps run 1 exposed, neither of them backend defects.**
First, D7 and D8 also ask that the now-unresolvable author renders gracefully,
and that could not be reached: comments exist only in feed view **by design**,
and the feed is empty when the viewer follows nobody — which is exactly the state
an erase leaves behind when the departing member was the only account they
followed. Verifying it needs a viewer who follows a third account. Second, the
avatar-propagation observation that narrowed C-34 and produced C-37.

`verify_jwt` is pinned in `supabase/config.toml` (`43be489`). Without it the CLI
defaults to `true` and any deploy from a clean checkout would silently change
the authorisation configuration of the deletion path as a side effect of
shipping unrelated code — caught before the B-20 deploy, not after.

**Retracted:** an earlier P0 asserted cross-user storage destruction via the
cleanup triggers. `pg_trigger` shows they are attached to nothing, so the attack
does not work. What survives is B-10.

## Verified sound — do not revisit

**Backend:** RLS enabled on every public table with policies.
`posts_select_public_or_owner` correct (private posts owner-only; public require
an approved follow). `connected_attachments` INSERT policy binds the storage
path to sender UID and asset ID; SELECT and UPDATE recipient-scoped. The
immutability trigger. All three comment RPCs validate properly.
`follow_requests_open` enforced. Buckets private, MIME allow-listed,
size-limited. `delete_account_v1` authorisation (subject derived from the
verified token, never the request body).

**Client:** attachment privacy fails closed; session deletion is fail-closed;
`StagingStore`'s file-backed design; all DEBUG bypasses correctly gated; no
hardcoded credentials; no analytics, crash-reporting or attribution SDK; the
three lifecycle paths (sign out / expiry / erase) are correctly separated and
cannot trigger one another.

## Lessons for future work

Several findings were wrong because behaviour was inferred from names and
structure rather than checked:

- A P0 was filed for cross-user storage destruction on the assumption that two
  functions named `cleanup_post_attachments_on_*` were triggers. They are
  attached to nothing.
- C-13 was filed P3 with "it terminates in practice." It cannot terminate; the
  compiler caught what a close read missed.
- An avatar-loss risk on expiry was asserted and turned out not to exist — the
  avatar is already written to the device-local namespace. **That clean answer
  then closed the subject.** It is the register's only avatar entry and it sits
  under *verified sound*; the opposite question — whether the *backend* copy is
  released when it should be, and whether a replacement reaches anyone — was
  never asked. C-33, C-34, C-35 and B-20 all came out of asking it later. The
  audit was organised by mechanism, which is why `delete_account_v1` carries
  seven findings that all land on attachments, comments, posts and follows, and
  none on step 4, and why `qa-plan` walks the attachments bucket through six
  destructive rows and the avatars bucket through none. **A clean verdict in one
  direction is not coverage of a subject.**

**Every identity field has two local scopes** — `profile.__local_etudes_profile__.*`
and `profile.<backendUserID>.*` — and four findings are now the same mistake in
that one design: C-19, C-27 and C-36 on location, C-34 on the avatar. The
recurring shape is a read or a write that picks one scope without a fallback, at
a moment when only the other scope is populated. When touching an identity
field, the question to ask first is *which scope holds this right now, and what
happens at the instant sign-in or sign-out flips the answer.*

**The Domain 3 expiry table makes six promises** (`architecture.md:76-83`). Five
now have findings or QA rows behind them. "Directory identity + avatar →
Deleted" was the sixth, and it was the one nobody had probed. Worth reading that
table as a checklist rather than as description.

**A finding read from source can be right about the mechanism and wrong about
the scope.** C-34 was derived correctly — the cache key really is
content-invariant and the `NSCache` really has no TTL — and then asserted that
every render site would serve the stale image until relaunch. Device evidence on
2026-08-11 showed two of them self-healing. The mechanism survived; the
prediction did not, because `NSCache` evicts on its own and views that are
recreated per presentation quietly refetch. **The trap is that a correct
mechanism makes the predicted consequence feel already verified.** It is not:
the consequence is a separate claim, and here it was the one that mattered,
because the sites that appear to work are the ones most likely to be spot-checked
and to produce a false all-clear. Two things came out of asking why: C-34
narrowed to the feed row, and C-37, a different site where the fetch is
unreachable by construction.

**Verify before asserting.** Cheap checks — a grep, a build, one query — have
repeatedly changed conclusions.
