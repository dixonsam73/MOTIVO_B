# Études — Audit Finding Register

From a four-phase client audit and a Supabase backend audit at commit `ec2f52f`,
plus the migration baseline builds. The audit itself compiled nothing except at
migration — findings marked *(build)* came from the Release compile.

**Severity:** P0 critical · P1 release blocker · P2 important · P3 improvement.

**State** — deliberately separate from severity, and the column that moves as
work lands:

| State | Meaning |
|---|---|
| **Confirmed defect** | The code is wrong today. Evidence is in hand. |
| **Unverified** | Suspected, mechanism plausible, not yet established. The cell says what would settle it. |
| **Confirmed gap** | Factually true and worth tracking, but not a defect in behaviour (coverage, tooling, process). |
| **Product decision settled** | We know what the correct behaviour is. The code does not do it yet. |
| **Resolved** | The implementation now matches the decision, and that has been verified. |

The distinction between the last two is the point of this register. An item
moves to **Resolved** only when code has changed and been checked — never
because a design was agreed. C-23 and C-24 are Resolved; both were filed during
Phase 1 rather than by the audit. C-1 is the first audit finding to move, and it
is Resolved **for its client scope only** — the server half is tracked separately
as C-26. Where a state is qualified like that, read the cell rather than the
word.

## Lessons for future work

Several findings were wrong because behaviour was inferred from names and
structure rather than checked:

- A P0 was filed for cross-user storage destruction on the assumption that two
  functions named `cleanup_post_attachments_on_*` were triggers. They are
  attached to nothing.
- C-13 was filed P3 with "it terminates in practice." It cannot terminate; the
  compiler caught what a close read missed.
- An avatar-loss risk on expiry was asserted and turned out not to exist — the
  avatar is already written to the device-local namespace. **That clean answer
  then closed the subject.** It is the register's only avatar entry and it sits
  under *verified sound*; the opposite question — whether the *backend* copy is
  released when it should be, and whether a replacement reaches anyone — was
  never asked. C-33, C-34, C-35 and B-20 all came out of asking it later. The
  audit was organised by mechanism, which is why `delete_account_v1` carries
  seven findings that all land on attachments, comments, posts and follows, and
  none on step 4, and why `qa-plan` walks the attachments bucket through six
  destructive rows and the avatars bucket through none. **A clean verdict in one
  direction is not coverage of a subject.**

**Every identity field has two local scopes** — `profile.__local_etudes_profile__.*`
and `profile.<backendUserID>.*` — and four findings are now the same mistake in
that one design: C-19, C-27 and C-36 on location, C-34 on the avatar. The
recurring shape is a read or a write that picks one scope without a fallback, at
a moment when only the other scope is populated. When touching an identity
field, the question to ask first is *which scope holds this right now, and what
happens at the instant sign-in or sign-out flips the answer.*

**The Domain 3 expiry table makes six promises** (`architecture.md:76-83`). Five
now have findings or QA rows behind them. "Directory identity + avatar →
Deleted" was the sixth, and it was the one nobody had probed. Worth reading that
table as a checklist rather than as description.

**A finding read from source can be right about the mechanism and wrong about
the scope.** C-34 was derived correctly — the cache key really is
content-invariant and the `NSCache` really has no TTL — and then asserted that
every render site would serve the stale image until relaunch. Device evidence on
2026-08-11 showed two of them self-healing. The mechanism survived; the
prediction did not, because `NSCache` evicts on its own and views that are
recreated per presentation quietly refetch. **The trap is that a correct
mechanism makes the predicted consequence feel already verified.** It is not:
the consequence is a separate claim, and here it was the one that mattered,
because the sites that appear to work are the ones most likely to be spot-checked
and to produce a false all-clear. Two things came out of asking why: C-34
narrowed to the feed row, and C-37, a different site where the fetch is
unreachable by construction.

**Verify before asserting.** Cheap checks — a grep, a build, one query — have
repeatedly changed conclusions.
